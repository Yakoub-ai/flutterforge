# Recipe: Firebase Authentication App

## What We're Building

A production-ready authentication flow using Firebase — email/password sign-up and login, Google Sign-In, email verification, and password reset. State management is handled with Riverpod. After signing in, users land on a simple home screen showing their profile info. The app handles session persistence (users stay logged in across restarts) and graceful error states. This is the auth foundation you drop into any app that needs accounts.

## Prerequisites

- Flutter 3.19+ and Dart on `PATH`
- FlutterForge plugin installed in Claude Code
- A Google account to create a Firebase project
- Android emulator or iOS simulator running
- `firebase-tools` CLI installed: `npm install -g firebase-tools`
- For Google Sign-In on iOS: a physical device or a simulator with a Google account signed in

## Step-by-Step Workflow

### Step 1 — Plan the App

```
/flutterforge:plan-flutter-app "I want to build a Flutter authentication app using Firebase. It needs email/password sign-up and login, Google Sign-In, email verification enforcement, and a password reset flow. State management with Riverpod. After auth, users see a simple home screen with their display name, email, and a sign-out button."
```

**What happens:** The product-strategist returns a brief focused on the auth journey — 3–4 user personas (new user, returning user, forgot-password user) and user stories covering the full authentication lifecycle including error cases (wrong password, email already in use, network failure).

The UX designer returns a screen map: typically 5–6 screens (splash/landing, sign-in, sign-up, email verification pending, forgot password, home). It will also describe transition animations and which screens are part of the auth flow vs the app flow.

The Flutter architect returns the state management design — usually a `StreamProvider` listening to `FirebaseAuth.authStateChanges()` that drives a `GoRouter` redirect, so users are automatically sent to the right screen based on auth state.

**Decision point:** The architect may propose `go_router` for navigation with auth guards. If you prefer a simpler `Navigator 2.0` approach without a router package, say so. For most production apps, accept the `go_router` recommendation.

Confirm with: `"Looks good, proceed."`

---

### Step 2 — Create the Firebase Project

Before scaffolding the Flutter app, set up Firebase. These are manual steps:

1. Go to [console.firebase.google.com](https://console.firebase.google.com) and create a new project. Name it something like `my-auth-app-dev`.
2. In the Firebase console, go to **Authentication → Sign-in method** and enable:
   - **Email/Password**
   - **Google**
3. Add your Android app in **Project Settings → Your apps → Add app**:
   - Package name: decide now (e.g., `com.yourcompany.myauthapp`). You cannot change this easily later.
   - Download `google-services.json`
4. Add your iOS app similarly:
   - Bundle ID: use the same reverse-domain pattern (e.g., `com.yourcompany.myauthapp`)
   - Download `GoogleService-Info.plist`
5. Log into Firebase CLI:

```bash
firebase login
```

Keep both downloaded config files handy — you'll place them in the project after scaffolding.

---

### Step 3 — Scaffold the Project

```
/flutterforge:new-flutter-app
```

**What happens:** FlutterForge asks for the app name and directory. Use the same package name you registered in Firebase (e.g., `com.yourcompany.myauthapp` as the org prefix, `my_auth_app` as the project name).

After the scaffold completes, place the Firebase config files:

```bash
# Copy google-services.json into the Android app folder
cp ~/Downloads/google-services.json android/app/google-services.json

# Copy GoogleService-Info.plist into the iOS Runner folder
cp ~/Downloads/GoogleService-Info.plist ios/Runner/GoogleService-Info.plist
```

Then run `flutterfire configure` to wire up the Dart-side config:

```bash
dart pub global activate flutterfire_cli
flutterfire configure --project=my-auth-app-dev
```

This generates `lib/firebase_options.dart`. Do not edit this file manually.

Verify the app still compiles:

```bash
flutter run
```

### Step 4 — Build the Auth Infrastructure

```
/flutterforge:build-flutter-feature "Firebase Auth infrastructure: initialize Firebase in main.dart using firebase_options.dart, create an AuthRepository that wraps FirebaseAuth, implement a Riverpod StreamProvider for auth state that emits User? (null when signed out), and a GoRouter configuration with an auth redirect guard that routes unauthenticated users to /sign-in and authenticated users to /home."
```

**What happens:** The inspect phase reads your current `main.dart`, `pubspec.yaml`, and folder structure. The plan phase shows exactly which files will be created and what each contains.

**Approval gate:** Review the router redirect logic carefully — this is the most logic-sensitive part. Confirm the guard handles three states: loading, authenticated, and unauthenticated. Ask for changes if the plan doesn't account for the loading state (a common bug where users briefly see the wrong screen on startup).

After implementation, hot-restart the app. It should show a blank sign-in placeholder (or redirect correctly) without crashing.

---

### Step 5 — Build the Sign-In Screen

```
/flutterforge:build-flutter-feature "Sign-in screen with email/password fields and a Google Sign-In button. Validation: email must be valid format, password must be non-empty. On submit, call AuthRepository.signInWithEmail. On Google button tap, call AuthRepository.signInWithGoogle. Show a loading indicator during the async operation. Show a SnackBar with the Firebase error message on failure. Include a 'Forgot password?' link and a 'Don't have an account? Sign up' link."
```

**What happens:** The agent implements the sign-in screen with proper error mapping. Firebase error codes like `user-not-found` and `wrong-password` are mapped to human-readable messages.

After implementation, test these scenarios manually:
- Submit with empty fields → validation errors appear inline
- Submit with wrong credentials → SnackBar with readable error
- Submit with valid credentials → navigates to home screen
- Tap Google Sign-In → Google account picker appears

### Step 6 — Build the Sign-Up Screen

```
/flutterforge:build-flutter-feature "Sign-up screen with name, email, password, and confirm-password fields. Validation: name non-empty, email valid format, password minimum 8 characters with at least one number, passwords match. On submit, call AuthRepository.createUserWithEmail, then update the Firebase user's displayName, then send a verification email. Navigate to an 'email verification pending' screen."
```

**What happens:** The agent creates the sign-up screen and an `EmailVerificationScreen` that shows a message asking the user to check their inbox, a resend button (rate-limited to once per minute), and a "I've verified, continue" button that calls `user.reload()` and checks `emailVerified`.

Test the sign-up flow end-to-end: create an account, check the verification email in your inbox, tap the link, return to the app, tap "I've verified, continue."

Show a success state explaining that an email was sent, with a back-to-sign-in button. ```

**What happens:** A focused, single-screen implementation. Note the security requirement in the prompt — the agent will implement the generic message by design.

### Step 8 — Build the Home Screen

```
/flutterforge:build-flutter-feature "Home screen that displays the authenticated user's avatar (from photoURL or a placeholder initial), display name, and email. Include a sign-out button. If the user signed in with Google, show the Google profile photo. Screen is only reachable when authenticated — the router guard already handles this."
```

**What happens:** A straightforward screen. The agent reads the `User` object from the `StreamProvider` already set up in Step 4.

### Step 9 — Handle Auth Persistence Edge Cases

```
/flutterforge:build-flutter-feature "Auth edge cases: (1) If a user tries to sign up with an email already linked to a Google account, show a prompt to sign in with Google instead and link the credentials. (2) If the app is opened while offline, show a network error state rather than hanging indefinitely on the loading screen."
```

**What happens:** The inspect phase will identify the current sign-up error handler. The plan will show how Firebase's `account-exists-with-different-credential` error code is caught and handled.

This is the hardest step in the recipe. Review the plan carefully before approving — credential linking has several edge cases. If the plan looks overly complex for your use case, tell the agent:

> "Skip credential linking for now — just show a clear error message telling the user to sign in with Google instead."

### Step 10 — Generate Tests

```
/flutterforge:generate-tests "Auth app: unit tests for AuthRepository (mock FirebaseAuth), provider tests for the auth stream, and widget tests for SignInScreen, SignUpScreen, and ForgotPasswordScreen. Mock FirebaseAuth with mockito."

**What happens:** The test engineer generates mocks using `mockito` or `mocktail`. Auth flows have many async paths — expect 20–35 test cases.

```

Pay attention to any tests that time out — they may indicate missing `await` in the auth repository.

### Step 11 — Audit and Polish

```
/flutterforge:audit-flutter-app
```

The security reviewer will specifically check:
- That error messages don't leak account existence (the password reset screen)
- That Firebase rules are not overly permissive (though auth rules are configured in the console, not the app)
- That the Google Sign-In client ID is not hardcoded in source (it shouldn't be — `google-services.json` and `GoogleService-Info.plist` are read at build time)

```
/flutterforge:improve-ux "authentication flow"
```

The UX agent typically recommends: keyboard-aware scrolling on sign-up (so the form doesn't hide behind the keyboard), focus traversal order on the sign-in fields (email → password → submit on next/done), and a biometric sign-in option for returning users.

### Step 12 — Prepare for Release

```
/flutterforge:prepare-release
```

For Firebase apps, the release engineer will specifically flag:
- SHA-1 and SHA-256 fingerprints must be registered in Firebase console for Google Sign-In on Android
- `google-services.json` and `GoogleService-Info.plist` must NOT be committed to public repos
- Add both files to `.gitignore`

Add to `.gitignore`:
```
android/app/google-services.json
ios/Runner/GoogleService-Info.plist
```

For team projects, distribute these files via your secrets manager (1Password, Vault, CI/CD secret environment variables).

## Tips for This App Type

**SHA fingerprints:** Google Sign-In on Android will silently fail if your debug SHA-1 is not registered in the Firebase console. Add it under Project Settings → Your apps → Android app → Add fingerprint. Get your debug SHA-1 with:
```bash
keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android -keypass android
```

**iOS Google Sign-In URL scheme:** `GoogleService-Info.plist` contains a `REVERSED_CLIENT_ID` that must be added as a URL scheme in `ios/Runner/Info.plist`. The Flutter Firebase setup docs cover this, but it is easy to miss. The release engineer in `/flutterforge:prepare-release` will catch this.

**Email verification enforcement:** If you want to enforce email verification at the router level (not just show a screen), add a check on `user.emailVerified` inside the GoRouter redirect callback. Users who skip verification are redirected back to the verification screen on every deep link.

**Riverpod `ref.watch` vs `ref.listen`:** Use `ref.watch` for the auth state on screens that should rebuild when auth changes. Use `ref.listen` in widgets that need to react to auth changes with side effects (like showing a snackbar after sign-out).

**Google Sign-In on simulator:** Works on Android emulator. On iOS simulator, you need to be signed into a Google account in the simulator's Settings app first, or use a physical device.

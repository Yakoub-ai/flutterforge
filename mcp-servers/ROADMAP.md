# MCP Server Roadmap

FlutterForge's original PRD specified three custom MCP servers that do not yet exist as
public packages. This document records their intended capabilities, explains what current
public servers cover in the meantime, and provides enough specification detail for
anyone who wants to build them.

---

## Status Overview

| Server                  | Status         | Notes                                    |
|-------------------------|----------------|------------------------------------------|
| `firebase`              | **Shipped**    | `firebase-tools experimental:mcp` in `.mcp.json` — see `README.md` |

| `appstore-readiness-mcp`| Planned        | Manual checklists + scripts              |

## 1. `flutter-docs-mcp`

### Purpose

A dedicated MCP server that speaks directly to the Flutter SDK documentation tree,
providing semantically-rich, version-aware answers about Flutter classes, widgets, and
APIs — without requiring a network round-trip to a third-party indexer.

### Current Workaround

`context7` fetches Flutter docs from the `flutter/flutter` GitHub repository and the
`api.flutter.dev` reference. It works well for stable-channel APIs and popular widgets
but has limitations:

- It cannot filter results to a specific Flutter version. A query for
  `NavigationBar` returns docs for the current HEAD, which may differ from the version
  pinned in `pubspec.yaml`.
- Queries are keyword-based; there is no widget inheritance traversal or property
  resolution across mixin chains.
- It requires a live network connection — offline development environments cannot use it.

### Planned Capabilities

```
resolveClass(className: string, sdkVersion?: string) -> ClassDefinition
  Returns: constructors, properties, methods, mixins, superclass chain, deprecation notices.

listWidgetProperties(widgetName: string, sdkVersion?: string) -> Property[]
  Returns: name, type, required/optional, default value, description, since-version.

searchDocsBy(term: string, sdkVersion?: string, category?: "widget"|"class"|"function") -> SearchResult[]
  Returns: ranked list of matching symbols with one-line descriptions and links.

getChangelog(fromVersion: string, toVersion: string) -> BreakingChange[]
  Returns: list of breaking changes, deprecations, and new APIs between two Flutter versions.
```

### Why It Is Better Than `context7`

- **Version-aware** — pins results to the Flutter version in `pubspec.yaml` or
  `flutter --version`, preventing documentation drift between major releases.
- **Semantic traversal** — `listWidgetProperties` walks the entire inheritance chain and
  resolves mixins, so you see all applicable properties rather than just the ones
  declared on the immediate class.
- **Offline-capable** — ships a local mirror of the SDK docs, regenerated during
  `flutter upgrade` by a companion CLI tool.
- **Breaking-change detection** — `getChangelog` lets FlutterForge's upgrade agent
  automatically flag call sites that use removed or renamed APIs.

### Approximate Build Complexity

Medium. The Flutter SDK docs are generated by `dartdoc` and published as structured JSON
at `api.flutter.dev/flutter/index.json`. The MCP server would parse this JSON, build an
in-memory index, and expose the four tools above. Estimated effort: 2–3 weeks for an
experienced Dart/Node.js developer. The main challenge is handling the version-snapshot
workflow so the index stays synchronized with `pubspec.yaml`.

## 2. `pub-dev-mcp`

### Purpose

A dedicated MCP server for querying pub.dev: searching packages, fetching metadata,
checking version compatibility, and finding alternatives. Replaces manual copy-pasting
from the pub.dev website.

### Current Workaround

`context7` can fetch the README and `CHANGELOG.md` of a pub.dev package by name. It
cannot:

- Run a ranked keyword search across pub.dev (e.g., "best HTTP client for Flutter").
- Check whether a set of packages are mutually compatible with a given Flutter/Dart SDK
  constraint.
- Find packages that are alternatives to a deprecated or abandoned one.

For compatibility checks, developers currently run `flutter pub outdated` and manually
inspect the output.

### Planned Capabilities

```
searchPackages(query: string, tags?: string[], sort?: "popularity"|"likes"|"pub_points") -> Package[]
  Returns: name, description, version, score, last-published date, null-safety status.

getPackageInfo(name: string, version?: string) -> PackageDetail
  Returns: pubspec.yaml contents, README, changelog, dependency graph, example links,
           publisher, license, pub.dev scores (popularity, likes, pub points).

checkCompatibility(packages: {name: string, version: string}[], sdk: {flutter: string, dart: string}) -> CompatReport
  Returns: per-package compatibility status, conflicting constraints, suggested resolutions.

findAlternativesTo(packageName: string) -> Alternative[]
  Returns: ranked list of packages with overlapping functionality, each with a comparison
           summary (maintenance status, null-safety, Flutter compatibility, license).
```

### Why It Is Better Than `context7`

- **Structured search** — `searchPackages` uses the pub.dev REST API directly, returning
  structured metadata rather than scraped README text.
- **Dependency resolution** — `checkCompatibility` runs the Dart `pub` solver against a
  synthetic `pubspec.yaml`, catching constraint conflicts before `flutter pub get` fails.
- **Alternatives discovery** — `findAlternativesTo` helps teams migrate away from
  archived packages or find lighter-weight options.
- **Live scores** — pub.dev popularity and maintenance scores are fetched in real time,
  not frozen in a documentation snapshot.

### Approximate Build Complexity

Low-to-medium. pub.dev exposes a public REST API (`pub.dev/api/packages/{name}`) and a
search endpoint. The compatibility check is the most complex piece — it either shells out
to `dart pub deps` or reimplements enough of the Dart version-solver to detect conflicts.
Estimated effort: 1–2 weeks. The MCP server can be written in Node.js or Python.

## 3. `appstore-readiness-mcp`

### Purpose

A dedicated MCP server that integrates with App Store Connect (Apple) and the Google
Play Developer API to automate pre-submission validation, screenshot requirement checks,
and metadata audits directly from the FlutterForge workflow.

### Current Workaround

The `/flutterforge:prepare-release` command and `release-engineer` agent rely on manual checklists
and the `flutter_build_ios.sh` / `flutter_build_android.sh` scripts. Developers must
open App Store Connect and the Google Play Console in a browser to:

- Verify that screenshot dimensions match the current device matrix requirements.
- Confirm that the app's privacy nutrition labels are complete.
- Check that the binary passes automated pre-review tests (age rating, export compliance).

There is no programmatic integration today.

### Planned Capabilities

```
validateMetadata(appId: string, platform: "ios"|"android") -> MetadataReport
  Returns: app name, subtitle, description, keywords — validated against character
           limits, prohibited terms, and localization completeness.

checkScreenshotRequirements(appId: string, platform: "ios"|"android") -> ScreenshotReport
  Returns: required device sizes, current upload status per size, any missing slots,
           dimension and resolution rules for the current App Store / Play Store spec.

getReviewGuidelines(category: string) -> GuidelineSection[]
  Returns: relevant App Store Review Guideline or Google Play Policy sections for the
           app's declared category, flagging common rejection reasons.

submitForReview(appId: string, platform: "ios"|"android", releaseNotes: string) -> SubmissionResult
  Returns: submission ID, estimated review time, any blocking issues found during
           pre-submission validation.
```

### Why It Is Better Than Manual Checklists

- **Screenshot matrix stays current** — Apple and Google update device size requirements
  when new hardware ships. The MCP fetches current requirements from the platform API
  rather than depending on a hardcoded checklist that goes stale.
- **Metadata character limits enforced** — common rejections (subtitle over 30 chars,
  keywords with commas) are caught before submission.
- **Integrated into the release workflow** — FlutterForge's `release-engineer` agent can
  call `validateMetadata` and `checkScreenshotRequirements` as part of the same session
  that builds the release artifact, reducing context switching.
- **Programmatic submission** — `submitForReview` eliminates the browser-based Transporter
  / Play Console upload flow for teams that have already validated their build locally.

### Authentication

- **iOS / App Store Connect** — requires an App Store Connect API key (Key ID, Issuer ID,
  and `.p8` private key file). The server generates short-lived JWTs for each request.
- **Android / Google Play** — requires a Google Cloud service account with the
  `Android Publisher` role, authenticated via a JSON key file.

### Approximate Build Complexity

High. Both platform APIs have non-trivial authentication flows, rate limits, and rapidly
changing screenshot/metadata specifications. The `submitForReview` tool in particular
must handle large binary uploads and asynchronous processing status. Estimated effort:
6–10 weeks, including test coverage against sandbox environments.

This is the highest-priority custom MCP because no public alternative exists — context7
cannot interact with App Store Connect or Google Play at all.

## Contributing

If you build any of these servers, please open a PR against the FlutterForge repository
and update the `.mcp.json` to reference the new package. Follow the naming convention
`flutter-docs-mcp`, `pub-dev-mcp`, and `appstore-readiness-mcp` so existing documentation
stays accurate.
